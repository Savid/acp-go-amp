---
title: Prompt Streaming
description: How one short-lived Amp process per prompt turns stream-JSON frames into ACP updates and results.
---

Each ACP prompt starts exactly one short-lived native process and streams its
output back as ACP `session/update` notifications, ending with a single
terminal result.

## The prompt process

```text
amp threads continue <thread> --stream-json --stream-json-input -x
```

The adapter always adds `--no-ide`, `--no-color`, `--no-notifications`, and an
isolated `--settings-file`. MCP configuration is supplied with `--mcp-config`
when the ACP session includes stdio or HTTP MCP servers.

## Frame mapping

Amp stream-JSON frames map to ACP updates:

- user text frames become user message chunks
- assistant text frames become agent message chunks
- tool-use frames become tool-call updates
- structured tool-result text and images become complete ordered
  `tool_call_update.content` snapshots
- usage data becomes ACP `usage_update`
- final result usage is copied to the prompt response

Main-agent message chunks carry a wrapper-derived UUID in `messageId` and
`_meta.amp.messageId`; the successful prompt response repeats the terminal
main-agent value. Amp exposes no native message/turn id, so the adapter anchors
the UUID to the exact raw frame and its durable transcript position. This keeps
load replay stable without modifying native mirror bytes.

The `usage_update` `size` field carries Amp's native `usage.max_tokens`
verbatim (a model-scale value Amp reports), or `0` when absent.

### Assistant text is append-only

`agent_message_chunk` and `agent_thought_chunk` are append-only deltas: a client
renders a turn's assistant text as the in-order concatenation of every chunk it
received, so no chunk repeats text the turn already streamed.

Amp streams one `assistant` frame per native message, and each text block in a
frame becomes exactly one chunk, in native order. The terminal `result` frame
carries the whole assembled answer in its `result` field, and this adapter reads
that field for **failure text only** — never as content — so a turn whose result
repeats the streamed text still publishes that text exactly once. A turn holding
a single assistant message yields exactly one chunk; a turn holding several
yields each message once. `TestAssistantTextIsAppendOnly` replays the native
fixtures in `testdata/stream-json/` and pins all three cases.

The rule binds text only. Agent images ride one chunk each, and
`tool_call_update.content` is a whole-array replacement by ACP definition.

No slash commands are advertised. Text like `/review` remains ordinary prompt
text and is sent to Amp unchanged.

ACP prompt image blocks are validated before the native process starts and are
sent as Amp stream-JSON base64 image sources in their original content order,
whether their bytes arrived as embedded base64 or through the local handoff form.
See [Models and config](/docs/features/models-config#image-input) for formats
and native envelopes, [Updates](/docs/reference/updates#image-tool-content) for
typed tool output, and [Session store](/docs/features/session-store) for replay
behavior.

## Cancel and stop reasons

`session/cancel` closes native input, calls `NativeProcess.Revoke`, and then
waits for `NativeProcess.Wait`. In managed mode the host authority owns the
complete native lease and its descendants. A wait or reclaim failure matches
`ampacp.ErrContainmentIncomplete`; the adapter commits no terminal state and
does not fall back to direct execution. Ordinary mode owns only the direct
same-identity child and publishes no authoritative quiescence claim.

A successful prompt returns exactly one terminal result, and its stop reason is
the native harness's own: `end_turn` for a completed turn, `cancelled` for a
cancelled one, `max_tokens` when the assistant frame reports a token ceiling,
and `max_turn_requests` when the native result reports a turn-request ceiling. A
ceiling is reported as the reason it is rather than as a clean end or a provider
failure. `refusal` exists in the ACP enum but Amp exposes no native signal for
it, so this adapter never produces it and a host must not wait for it.

## Turn failures and timeouts

A native turn failure is never reported as a stop reason. It terminates
`session/prompt` with a JSON-RPC error (`-32603`) carrying:

```json
{
  "error": "amp_turn_failed",
  "cause": "process_exit" | "transport" | "provider" | "timeout",
  "message": "<real native cause>"
}
```

`message` always carries the real native cause (exit status and stderr tail for
a process exit, the decode/read error for a transport fault, or `result.error`
falling back to `result.result` for a provider error) — never a fixed
placeholder. The session stays addressable and retriable after such a failure; a
follow-up `session/prompt` re-drives the turn.

`amp_turn_failed` is the **prompt turn's** envelope and the only `-32603` shape
that carries native text. Every `-32603` away from a prompt turn — and a prompt
refused before its turn starts, such as one addressed to a poisoned session or to
a session whose native thread is gone — carries a closed `amp_`-prefixed token
with no `message` member at all. See
[ACP methods](/docs/reference/acp-methods#internal-errors-away-from-a-prompt-turn).

An image the adapter will not ship is refused in place: fixed guidance takes
the image's position in that tool call's own content and the turn keeps
running with its context. Only the adapter's own artifact store breaking uses
the `-32603` envelope with `cause: "transport"`, plus `stage: "image_output"`
and `reason: "storage_failed"`; there the adapter emits failed status for the
originating tool call and interrupts the turn. Neither path turns the failure
into an empty image or silently successful text.

<Note>
`WithTurnTimeout(d)` sets an optional per-turn deadline (default `0`, no
deadline). On expiry the adapter aborts the native turn and returns the failure
error with `cause: "timeout"` — a timeout is a failure, not a cancellation, so
it never produces a `cancelled` stop reason.
</Note>
